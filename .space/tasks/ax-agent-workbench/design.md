# 作業を行うエージェントの保存・実行・登録

2026-10-07。基点 `ede929e`。私有ファイルと隔離Pythonの試作は検証済み。AX統合・登録運用は実装を進める。人間への確認中事項は[依頼記録](task.md)に残す。

## 目指す利用例

利用者が「部門別の売上合計と件数をExcelにしてください」と依頼し、CSVまたはExcelを添付する。エージェントは必要な条件を質問し、Pythonで集計して、結果を確認してからダウンロードできるファイルを返す。同じ処理をスキル・エージェントとして登録し、本人用またはワークスペース共有で使えるようにする。定期実行も同じ定義を利用する。

作業を進めるRuntimeは一つ。Pythonを実行する別Taskは計算用の環境であり、サブエージェント機能は追加しない。

## 保存構造の比較

独立候補は[A：PG中心](design-candidates/a.md)と[B：PGと外部ストレージ](design-candidates/b.md)。AX内RuntimeとAX外の本人・費用管理という既存判断は両案で維持する。

| 判断軸 | A：PostgreSQLに定義・小さいファイルを保存 | B：定義台帳はPostgreSQL、本文・ファイルは外部ストレージ |
| --- | --- | --- |
| 初期の運用 | 現在のDBで保存・権限・バックアップを管理できる | ストレージの資格情報、バックアップ、不要ファイル回収も必要 |
| 版とファイルの確定 | 同じDBの更新で内容と参照を確定できる | ファイル確定→DB参照公開の順序と部分失敗への対応が必要 |
| CSV/Excelの増加 | ファイルが増えるとDB容量・バックアップが重くなる | 大きいファイルや多い成果物を分離しやすい |
| 将来の移行 | 安定したfile IDとhashで参照し、保存先だけを移す設計が必要 | 最初からファイル容量をDB外へ置く |

採用する保存構造はA。初期はサイズを制限し、本文・参照ファイル・入力・成果物をPostgreSQLに保存する。読み書きする側はfile IDを使い、DB列やTaskのパスを保存先として扱わない。大容量・大量履歴が必要になった場合はBへ移す単位を設ける。Bの組込み原本と利用者編集版を分ける方針は取り込む。外部ストレージの製品選択や新規サービスの配備は、この段階では追加しない。

## スキルとプロンプトはどこに置くか

| 内容 | 保存先案 | 編集と実行 |
| --- | --- | --- |
| 製品の基本指示、組込みスキルの原本 | 開発時にGit管理し、製品へ同梱するファイル | リリースと一緒に検証する。画面編集では原本を上書きしない |
| 画面登録したスキル本文、参照資料、script | app PostgreSQLのスキル・版・ファイル | 下書きから公開版を作る。scriptは登録しただけでは実行権限を持たない |
| エージェントの指示文・選択スキル・許可する道具 | app PostgreSQLのエージェント定義と版 | 公開時にスキルの版も固定する。画面で作成・編集・複製する |
| 実際に使った指示・スキル・入力の組合せ | app PostgreSQLの実行記録 | 実行開始時に版ID・hashを固定し、後の編集を途中へ反映しない |
| 入力CSV/Excel、作成したファイル | app PostgreSQLの本人所有ファイル | 定義共有とは別に認可する。Taskへ渡すのは実行に必要なコピーだけ |
| 実行中の作業ファイル | AX Taskの一時作業領域 | 成果物を回収・保存してから停止する。永続保存の正本にしない |

スキルは[Agent Skillsの形式](https://agentskills.io/specification)に合わせ、`SKILL.md`と必要な`references/`・`scripts/`・`assets/`を一つの版として扱う。形式への適合や`allowed-tools`の宣言を、アプリの権限付与の代わりにはしない。

実行時は製品に同梱したファイルを読み、Gitサービスへの接続を要求しない。組込みスキルは原本のdigestを持つ初期公開版として登録し、利用者は複製して編集できる。編集可能なエージェントの指示と、実行制御・予算・権限は分ける。指示文を変更しても、使える道具や費用枠は増えない。

共有範囲は本人用とワークスペース共有の両方を持つ。本人用もWorkspaceごとに分離する。共有用は全メンバーが登録でき、作成者とWorkspace管理者が編集・公開できる（2026-10-07の人間回答）。共有定義が非公開スキルや本人の入力ファイルを暗黙に参照しないよう、公開時に依存関係を検査する。定義作者・管理者に実行者のチャットや成果物の閲覧権を付けない。

## 実行の流れ

```mermaid
flowchart LR
  Web[Webで依頼・ファイルを登録] --> DB[(PostgreSQL\n定義・版・本人のデータ・状態)]
  DB <--> Control[Goの実行管理・Gateway]
  Control --> Plan[AX Runtime\n依頼の理解・道具の提案]
  Plan --> Stop1[状態保存・停止確認]
  Stop1 --> Code[別のAX Task\n隔離したPythonで計算]
  Code --> Stop2[成果物の回収・停止確認]
  Stop2 --> Check[新しいAX Runtime区間\n結果確認・返答]
  Check --> DB
```

APIのHTTP処理内でPythonを起動しない。現在の同時実行枠1を保ち、前段の実停止を確認してから次を始める。人の回答待ちでは状態と使用量を確定し、実行環境を止めて枠を空ける。

ファイル搬送には、小さいテキスト要求とは別の制限付き転送契約を作る。本人・選択Workspace・file IDを照合し、分割転送と長さ/hashの確認後に入力を確定する。名前をshellへ埋め込まず、入力や成果物のsymlink・親ディレクトリ参照を拒否する。応答を失っても同じ確定ファイルを再参照でき、Taskの再実行とは分ける。

Python用Taskにはモデル鍵・DB資格情報・ストレージの資格情報・Runtimeのmailboxを渡さない。Python標準機能と検証した表計算用ライブラリを版固定で用意する。Excelの解析も隔離環境で行う。ネットワーク経由の任意パッケージ導入は、最初の集計経路に必要な条件として追加しない。

Pythonが書いたstdout・receipt・manifestは未信頼の出力として扱い、権限・使用量・費用・実停止・checkpointの正本にしない。子と子孫の停止を確認してから、信頼済みcollectorが許可名・配下限定・通常ファイル・サイズ・hashを検査し、確定した成果物だけを保存する。次のRuntimeは外部の確認済み状態と選別した結果を読み、Python module・pickle・プロセス状態を復元しない。

gVisorを使うだけで全通信や制御RPCから隔離できるとは扱わない。信頼済みrunnerと未信頼Pythonのユーザー・ファイル・操作可能なsyscall・資源を分ける構成を試作し、実Actorで検証する。固定版で必要な境界が成立しなければ、任意Pythonの開放前に基盤側を修正する。調査結果は `isolation-investigation.md`、試作後の実測は別に記録する。

固定runscの[実測](runsc-probe.md)では、OCI内tmpfsのnr_inodes指定が効かず、試作はコード実行前に拒否した。信頼側のLinux tmpfsを上限付きで作り、bind経由で渡す診断ではinode上限が効いた。以後はこの方式のcode専用profileを検討する。guestのfilesystem表示を信頼側設定の代用にせず、image/templateの厳密な選択、mountの作成・検証・停止・後片付けとsnapshot禁止を合わせる。Docker試作の成功だけで任意Pythonを有効にしない。

## 複数段階と利用上限

Runtimeの提案を質問・Python実行・完了・未対応の型に分け、外側で本人の許可と予算を検査する。各段階には一意IDと要求hashを持たせ、未確定の開始やモデル送信を自動で再送しない。途中で落ちた場合も、既送信の照合・回収・停止と、新しい実行を分ける。

各Taskの開始intent、モデルの計数・生成直前、保護ファイルの再利用で、現在の本人・所属・対象版の利用権・停止・grant・累積残予算を再確認する。旧有料runと新しい手動/定期の実行を同じ費用guardへ含め、二重計上や新経路だけの抜け道を作らない。未知usage・予約未精算・未停止runは共通holdを維持する。失効後も既送信の精算・回収・遮断・停止は限定service権限で続ける。

現在の3モデル要求・2tool・入力6000/出力512・実作業90秒は短文試験向けで、質問→計算→結果確認や修正の繰返しには不足し得る。回数の数え方を変えて制約を避けず、新しい限定profileを具体化して人間に確認する。総費用2,000円を維持する。0.01 USDの全体試用停止条件を引き上げる場合も、人間に変更内容を示す。

承認済みの新しい試験profileは、root全体でモデル最大6回、道具最大8回（うちPython最大3回）、実作業300秒、概算0.01 USD。検証全体の概算停止を0.05 USDとする変更は2026-10-07の人間回答で承認済み。各送信・実行前に予約し、上限まで繰り返すことを目的にしない。トークン配分は費用枠内で別途確定し、現在の1回あたり入力6000／出力512（思考込み）をこの承認だけで引き上げない。root全体は各呼出しの使用量を累積し、回数と予約費用の両方で止める。計数通信や請求集計の差を含む実請求の絶対保証ではない。API再試行0と費用不明時の停止は維持する。定期実行の許可期間・回数・費用は、これと別に有効化時の条件を定める。

## 登録画面と定期実行

画面はスキル、エージェント、定期実行の三つの管理対象を持つ。エージェントを選んで実行する入口と、定義を編集する入口を分ける。画面に内部のTaskや保存テーブルの操作を要求しない。

定期実行は作成者に属する独立した実行許可を持ち、Webログインのtokenを延命しない。ログアウト後も継続し、結果は作成者だけが閲覧する。所属・必要権限の喪失、予定の停止、許可期限・回数・費用枠の到達で新しい処理を止める。再加入で過去の許可を復活させない。現在の失効判断はapp DBを根拠とし、外部IdPの全token即時失効を実装済みとはしない。

予定日時ごとに一度だけ受付を確定する。前回が実行中・回答待ち・状態不明なら次を重複起動せず記録する。定義を編集しても登録済み予定の版を勝手に変えない。定期実行で使用する入力を固定するか、利用者が更新したデータセットの最新確定版を使うかは確認が必要。

最初は毎日・毎週と実行時刻を設定する案とし、画面で次回時刻とtimezoneを確認できるようにする。定期実行を有効にする操作には期間・最大回数・費用枠を含める。検証環境で有料処理を無期限に動かしたままにはしない。

## 進め方

1. ファイル保存・版管理と、CSV/Excelの隔離実行を無課金で試作する。独立した期待値で集計結果を照合し、通信・ファイル・制御RPC・資源制限と実停止を確認する。
2. 一つのRuntimeがPython実行結果を受け取って次へ進む経路を実装する。UIの依頼→必要な確認→集計→ファイル取得をつなぎ、型・DB・ブラウザ・実AXで検証する。
3. スキル・エージェントの登録、公開版の選択、本人用/共有の権限を画面へ追加する。
4. 定期実行の登録・開始・停止・履歴を追加する。多重起動、ログアウト、失効、予定編集時の競合を検証する。

v1〜v5 SQLと保存済み履歴は変更しない。追加移行で新しい版・ファイル・段階・定期許可を導入し、旧対話の利用と回収を保持する。利用経路ごとに完成・検証した単位でPRへまとめ、設計資料の更新だけでは作成しない。

独立比較もAを推奨した。[設計レビュー](design-review.md)の必須補足である未信頼出力の扱いと開始ごとの認可・共通guardを上記へ反映した。比較・文章の確認であり、隔離・資源制限や新しい利用経路の実機合格ではない。人間の未回答に依存しない本人ファイル保存と無課金の隔離試作から着手する。
