# 本人用ファイルの初期契約

2026-10-07。設計Aを土台に、共有定義の未決方針と独立して実装する保存単位。稼働DBへの適用・製品全体の公開は親の統合後に行う。

- ownerはAPIが確定した内部user UUID、workspaceは現在所属を検証したID。アップロード・一覧・読取り・確定で両方を検査する。Workspace adminにも他人のファイルを公開しない。
- この段階は本人アップロードのみ。共有スキルの添付やcontroller成果物の登録権限は、対応する利用経路の設計後に追加する。
- 対象はCSV（UTF-8）と非暗号化 `.xlsx`。保存層は実bytes・長さ・SHA-256を管理し、Excelの解析・マクロ/式/外部リンクの扱いは隔離側で確認する。ファイル名やブラウザのmedia typeだけを内容の安全性の証拠にしない。
- 初期profile `work-file-v1`：1ファイル8MiB、転送chunk32KiB、同時draftは本人4件、本人の保存総量256MiB、アプリ全体1GiB。draftの予約容量も総量へ算入する。これらは初期の運用設定で、上限超過は明示拒否する。
- UUIDのfile IDを保存先から独立した参照とする。スキルや実行からDB列・Taskのpathを直接参照しない。
- 受付はidempotency keyと要求の同一性で一意。異なる本文でのkey再利用は拒否。同じ位置の同bytes再送だけを許可し、内容不一致を上書きしない。
- `uploading`と`ready`を分ける。期待した全chunk・総長・hashが一致したときだけ原子的にreadyにし、以降bytesは不変。途中の入力を実行や通常downloadへ渡さない。
- 存在しないID・他人・他Workspaceへのアクセスは内容を漏らさず拒否。失効した所属のuploadを継続・sealしない。中途半端なstageはモデルやTaskへ渡らない。
- 完成ファイルを自動削除しない。draftの取消は本人の明示操作とし、予約容量の解放は一回のみ。自動GC・長期retentionはこの単位で確定しない。
- 退出したWorkspaceのdraftが本人全体の上限を塞がないよう、現在所属するWorkspace画面から「利用できなくなった未完了送信を取り消す」を本人が明示実行できる。認証済みowner、現在画面の所属、対象の同owner・uploading・現在所属なしを検証する。旧Workspaceの本文・metadataを返さず、取消件数だけを返す。readyは対象外。再加入・seal・chunkとの競合を考慮し、所属を取り戻したdraftを失効扱いで消さない。
- 新しいschema-v6.sqlへ追加し、v1〜v5とchecksumを変更しない。APIは必要関数のみ呼べるよう限定する。既存の費用/実行台帳へ保存ファイルの権限を迂回する経路を追加しない。
- 専用の試験PGで、正常なCSV/XLSX bytes、全境界、本人/Workspace/失効、同key/競合、chunkの順序・重複・欠落・hash不一致、sealの同時実行、draft取消と容量、限定ロールを検証する。ライブラリの内部実装を写した試験より、利用者のアップロード→再取得が成立する契約を確認する。

担当BはSQL・保存クラス・共有型・移行入口・保存試験を所有する。API公開とWeb UIは親が後で統合する。モデル・AX・稼働DBの操作は行わない。
