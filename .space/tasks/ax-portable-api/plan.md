# 共通APIとPostgreSQL保存への移行計画

2026-10-06。対象main `0b6b4c8`。[設計](design.md)のBを実装する。内部の確認単位をPRの数と結び付けず、一つの構成変更としてまとめる。PR方針の修正、設計補足、実装、テスト、運用手順を同梱する。

## 完了条件

- C1: Hono/TypeScriptが所有者確認・受付・会話・実行・成果物の取得を直接処理し、共通APIの経路にPython・CLI・永続ローカルファイルを要求しない。
- C2: 既存app PostgreSQLへ会話・要求・実行履歴・成果物bytesを保存する。全件移行はID・owner・順序・ハッシュ・費用・未知状態を保ち、旧データを保全する。
- C3: 実行管理はHTTPの寿命から独立し、Task内Pythonを保つ。二重送信・費用・未知usage・全体実行枠・復旧時再開始禁止を維持する。CLIなしの実AX offlineで回収・遮断・実停止を確認する。
- C4: 共通APIをWorkers互換環境と通常Node環境で確認する。起動・設定・DB接続の環境差を限定し、クラウド固有機能を業務処理に必須としない。
- C5: 2利用者・旧ownerなしの隔離、全writerの切り替え、旧操作経路の拒否、再起動・復旧を確認する。復旧不能なデータ損失を起こさない。
- C6: 変更に適した局所・結合・実利用試験と独立レビューを終え、関連文書・知識を更新し、意味のある一つのPRとして納品する。

## 所有範囲と依存

| 単位 | 所有者 | 書き込み範囲 | 成果物と依存 |
| --- | --- | --- | --- |
| execution | 実行接続担当 | 新規 `execution/` とその検証資料 | P1のnative AX/guest/Substrate接続・停止確認を先に実証し、DB契約確定後に常駐実行管理へ接続する。Task内部のプロトコルを変える場合は先に親へ提示 |
| data-api | データ/API担当 | 新規 `web/data/`、`web/api/run-service.ts`・`chat-service.ts`、関連するAPIサービス試験 | 既存Pythonの契約・費用・会話を照合し、外部操作IDの契約確定後にDB保存とTypeScriptサービスを実装。auth領域、起動口、packageファイルは親が所有 |
| portability-migration | 親 | API起動・認証/設定の環境境界、依存定義、移行/運用ツール、CLI切り替え、資料、結合試験 | data-apiとexecutionの契約をつなぐ。schema本体やGo実行管理は各担当に修正を依頼。実環境の変更・データ移行は親に集約 |
| review | 独立確認担当 | 読み取り専用の調査・レビュー | 原則として対象実装を書いていない担当が、移行・認可・外部副作用・実証範囲を確認 |

共有のDB契約はデータ/API担当が作成し、実行接続担当と親が確認してから実装を結合する。必要な中間成果を同じブランチで利用できるが、他担当の変更を戻さない。DB・Kubernetes・稼働Web/APIへの変更は親が直列に行う。Taskのpaid経路は動かさず、offlineと模擬障害で検証する。

## 工程と証拠

既存2候補と独立比較は、同じ責務・保存要件に適合するため再利用する。接続試作で境界の変更が必要になれば設計へ戻る。新しい安全性の前提はblast-radiusでコードと実行結果を照合する。新機能の意味のある挙動試験を追加し、既存の認証・チャット契約試験を引き継ぐ。

1. 接続と停止証明をモデルなしで試す。未開始、開始応答不明、結果回収後、通信遮断・停止失敗の境界を具体化する。
2. 分離した試験DBへ保存領域を作り、受付・会話末尾・global guard・結果公開をトランザクションで確認する。
3. TypeScript API、DB、実行管理を結合する。所有者別の全操作、同keyの再送、別内容、競合、未知usage、壊れた成果物を試す。
4. Workers互換性、通常Node、実Web/BFFの経路で受付・表示・再起動後の保持を確認する。
5. 書き込みを止めた状態で既存記録をバックアップ・検査・取り込み・全件照合する。未確認の外部実行があれば切り替えず、根拠を調べる。旧CLI/直接操作の経路を制限し、新規受付後に古いファイルへ単純に戻せない点を手順へ記す。
6. 独立レビューの指摘を反映し、必要な範囲だけ再検証して納品する。

取得した証拠はverification.mdへ結果と版を伴って保存する。生の会話本文・秘密値・モデル鍵・認証トークンを記録しない。長時間作業の節目で状態を台帳に反映し、途中でPRを作らない。
