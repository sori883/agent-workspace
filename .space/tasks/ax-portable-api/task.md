## 依頼と終了地点

2026-10-06。共通APIが同じホストのPython・CLI・永続ファイルを必要とする構成を見直し、会話と実行記録の管理、AXへの接続、データストアへの移行を整理する。今回は設計・作業計画の提示まで。利用者の補足により、Cloudflare Workersは配置先候補の指定ではなく、共通APIの移植性を測る基準として扱う。

## 既存の条件

- 共通APIに認証済み利用者の会話・実行記録の管理を集める。Task内部のPythonエージェントを今回書き換える必要はない。
- PostgreSQLの配置をKubernetes内に固定しない。ローカルDockerの既存DBを開発に利用できる。
- 所有者・会話順序・送信の重複防止を維持する。所有者不明の既存記録をログイン利用者へ自動割り当てしない。
- 全利用者と運用CLIを通じた実行数・費用の制限、利用量不明時の停止、通信遮断と実行環境の停止確認を維持する。
- 障害復旧を理由にモデルを自動で再実行しない。外部起動の成否が不明なら照合まで保留する。

## 工程

devlowの設計工程を適用し、既存のPython再利用の理由をwhyで確認した。元の理由は、Python CLIに集めた実行記録・費用・排他制御をWebでも共用することだった。配置先の自由度が新しい条件となったため、構造を再検討する。

独立候補はA「共通APIと永続ワークフローからAXへ接続」、B「共通APIとAX付近の実行コントローラーを分離」。候補担当は各候補文書だけを編集する。候補作成に参加していない担当が比較と統合案の確認を行う。

比較基準は、APIのPython・ローカルファイル依存の解消、AX内部実装への結合、障害時の二重実行防止、認可と記録の一貫性、配置先への依存と運用負担、既存CLIを含む移行可能性。APIが外部の処理を呼べることだけで完了とはしない。
