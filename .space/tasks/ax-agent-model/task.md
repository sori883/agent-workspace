# AX対話ランタイムの実モデル接続

## 依頼と終了地点

2026-10-07の「まず別モデルから」を、直前に提案した模擬応答から実モデルへの接続として引き受けた。既存の低価格モデルを使い、Webで依頼→必要なら質問→本人の回答→成果物まで確認する。サブエージェント、任意コード実行、外部システム連携は後続に残す。

基点は main `13eb7f118c4bf8af7cdd4d6ae84d27d37f2c42aa`（PR #18）。AX Task内ランタイムとAX外Gateway・会話・認可・費用台帳という採用済み構成を再利用する。今回の設計対象は実モデルの送信、利用量精算、同意と表示の追加部分。

ユーザーの費用上限2,000円と試用停止目安0.01 USDを引き継ぐ。開始時の記録済み概算は0.00358975 USD、未解決実行0。上限・プリペイドを増やさない。送信前確認→最少回数の実呼び出し→結果確認の順とし、失敗や利用量不明時は連続送信せず調査する。検証後は外部送信を閉じる。

## 作業単位と所有範囲

最新状態は `orch/` 台帳を正本とする。親が記録を代行し、実際の担当・検証者を証拠に記す。

- Gateway担当A: execution/のprovider、controller、settings、Pythonランタイムと対応テスト。送信先固定、再試行なし、鍵をTaskへ渡さない、送信前制限と利用量を扱う。
- 台帳担当B: web/data、web/api、web/shared、移行入口と対応テスト。追加v5移行、modeと同意の固定、認可・予約・精算・既存費用ガードを扱う。稼働DBは変更しない。
- 親: UI、配備と実操作検証、統合、設計文書と知識保存、一つのPRでの引き渡し。稼働環境・秘密を扱う操作は親だけが実施する。
- レビュー担当: 共通契約および実装の独立レビュー。課金境界、認可、二重送信、失敗時の保留を優先する。

共通契約を先に固め、各担当の変更は同じブランチで統合する。既存schema-v1〜v4と旧previewの保存済み入力・ハッシュは変更しない。受け渡し後に親が全体を実経路で確認する。

## 受け入れ条件と検証

1. 既存previewは無課金のまま動き、実モデルは明示した同意をもって開始する。rootのmodeを回答時に変更できない。UI・API契約・移行テストで確認する。
2. 所有者、在籍、失効、停止、費用と呼出上限を送信前に検査する。鍵はGatewayのみが保持する。Go・PGの拒否系、再送、停止、利用量不明を検証する。
3. 成功と費用確定を分け、実利用量は外部Gatewayの台帳を正本にする。回答形式不正でも既知費用を失わず、不明時は予約と停止を残す。
4. Web→API→PG→AX→Gateway→実モデル→質問/回答→成果物の実経路を確認する。原則1 root・生成2回以内、全体最大3回・API再試行0・入力は累積6000を目安に事前計数＋128トークンの余裕をもって送信可否を決め、実usageの超過は記録して停止する。出力は思考込み累積512、稼働90秒。0.01 USDは公開単価に基づく予約・実績による停止ガードで、請求額の絶対上限保証ではない。送信ごとに結果と費用を確認する。
5. 独立レビューの必要修正、型・ビルド・関連回帰、移行と稼働確認後、一つのPRを作成して既存方針に沿ってマージする。秘密や生の認証ログを成果物へ含めない。

## 実装の受け入れ

実モデル2区間の質問→回答→本文生成、本人限定、使用量・費用と実停止を確認した。有料送信を閉じた後の無料previewも成功した。型・build・Node114件・ブラウザ7件・Go race/vet/build・固定SDK試験が成功し、独立レビューに残る必須指摘はない。条件と限界は[検証記録](verification.md)、[統合レビュー](integration-review.md)を参照する。
