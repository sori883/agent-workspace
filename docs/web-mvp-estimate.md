# 次の作業：ローカルWeb版の概算

2026-10-06時点の[概略設計](web-architecture.md)に基づく当初見積もり。現在は[W1のWebとAPIの土台](../web/README.md)を実装し、次はW2のAX操作接続。以下の工数は当初の概算を残しており、実績値ではない。工数は一人で実装・検証する場合の作業量を人日で表した概算（1人日＝8時間）であり、AIの実行時間や経過日数ではない。過去の同種実装の実測値に基づく見積もりではなく、既存コードと未実装範囲からの判断である。

## 次の区切りとして提案する範囲

ローカルのブラウザで指示と少量のテキスト入力を渡し、React RouterのBFF、共通バックエンド、既存AXを経由してタスクを開始し、状態・成否・成果物・使用量を確認できるところまで。

既存PythonのAX操作を共通バックエンドの内部実装として再利用する前提で見積もる。AX内のPythonエージェント、既存のkind・イメージ・費用台帳を維持する。タスクの制約は既存の少量UTF-8入力と成果物1件を引き継ぎ、チャット履歴や自由なコード実行へ広げない。

Web/BFFと共通APIはローカルの単一利用者・単一バックエンド・同時実行1件に限定する。共通APIをブラウザから直接呼ばず、BFFを経由する。公開用の共通ログインが未導入の間はループバックに限定し、ローカルセッション・入力検証・要求元確認・CSRF対策を含める。この状態を複数利用者向けの認証済みサービスとは扱わない。

## 工数の内訳

| 単位 | 作るもの・完了条件 | 概算 |
| --- | --- | --- |
| W1：WebとAPIの土台（完了） | React RouterのSSR/BFF、Hono共通API、ローカル起動方法、設定境界。ブラウザ→BFF→共通APIの疎通を確認する | 0.5〜1人日 |
| W2：AX操作の接続 | 既存Python処理の内部呼び出し、実行受付とID、状態・結果の照会、永続記録への対応。HTTP応答後も管理し、既存の費用台帳と排他を維持する | 1.5〜3人日 |
| W3：操作画面 | 指示・テキスト入力、実行操作、実行一覧・詳細、成果物と使用量・失敗理由の表示。受付の冪等性に沿って二重送信を扱う | 1〜2人日 |
| W4：利用経路と失敗時の検証 | ブラウザから実AXのoffline経路を通し、正常終了と成果物を確認する。二重送信・再起動・使用量不明・通信遮断や停止の未確認時に再実行しないことを検証し、必要な修正・レビュー・手順を反映する | 1〜2人日 |
| **合計** | **ローカルWeb版** | **4〜8人日（32〜64時間）** |

単位の時間には各部分の通常の実装・局所検証を含む。W4は結合経路と復旧条件の確認であり、全てのテストを最後まで先送りする意味ではない。初回見積もりの幅が大きいのは、CLIのホスト依存をどこまで分離する必要があるかと、HTTP再送・プロセス再起動時の状態管理が未実装のためである。

W1で起動方法とAPIの入出力の骨組みを決め、W2で開始・照会・回収の契約を確認する。W3はその契約に合わせて作り、W4で全体の操作経路を確認する。最初の着手単位はW1のみ（0.5〜1人日）とすれば、人間が画面と接続関係を確認しながら進められる。W1のAX操作は模擬応答でよく、実AX接続やモデル呼び出しを完了条件にしない。

W1のファイル配置・入出力・起動方法は[WebのREADME](../web/README.md)、設計比較と検証結果は[作業記録](../.space/tasks/ax-web-foundation/task.md)に記録した。W2以降の詳細な実装計画は各単位の着手時に決める。

## 共通認証を含める場合

ローカルのKeycloakを使った標準OIDCログイン・ログアウト、BFFのセッション、共通APIのトークン検証、タスク所有者によるアクセス制限、権限違反の試験までを追加すると、**さらに2〜4人日**を見込む。ローカルWeb版との合計は**6〜12人日（48〜96時間）**。

既存の社内Entra IDへの接続やCognitoの設定、テナント管理者との調整、アカウント移行・詳細なロール設計は含まない。Keycloakの製品採用を確定する見積もりではない。外部公開・複数利用者の運用を行う前に共通認証と必要な権限確認を実装・検証する。

## 今回の概算に含めないもの

- AWS/EKS/ECSへの配置、IaC、クラウド費用算出、本番の可用性・運用構築。
- RAG・記憶・MCP・追加のモデルアダプター。
- AX操作のTypeScript全面移植、gRPCだけによる既存フローの全面置換。
- 複数バックエンド・複数利用者・並列タスク、既存ファイル台帳のDB全面移行。
- 仕上げた画面デザイン、会話型チャット、リアルタイムのトークン配信。

これらを次の範囲に含める場合は別途見積もる。特にPython再利用をやめる場合、既存の費用・開始・復旧制御の移植と同等性検証が増えるため、この工数をそのまま流用しない。

## 費用と検証の前提

次のローカルWeb版の受け入れは、既存のofflineアダプターを使い、モデルAPIへの送信なしで確認する。無料の経路確認をAIの回答品質の検証と同一視しない。実モデル連携の追加確認が必要になった場合は、その目的・送信条件を別途整理し、設定済みの利用上限・費用ガードを維持し、成果のない反復送信を避ける。見積もり作業ではモデルAPIへの送信・AWSリソースの作成は行っていない。

根拠は [task_cli.py](../ax-local/task_cli.py) の同期実行、ローカル台帳・ロック、費用ガード、開始と回収・復旧、および [タスクCLIの利用手順](../ax-local/task-cli.md) の利用制約。見積もり作成時はWeb・BFF・共通API・OIDC接続が未実装で、アプリの起動やテスト再実行も行っていなかった。その後W1でWeb/BFFと模擬APIのHTTP経路を検証したが、これは実AX接続の確認ではない。OIDCは引き続き未実装。
